HIGH AVAILABILITY

Multi-Region Triple-Cluster Failover

Application · Redis · Kafka · Elasticsearch

Problem
A single cluster in one region served all traffic, with only Redis running in a dual configuration. There was no second cluster to fail over to, and a region-level failure took everything.
Constraint
The migration had to run with no service downtime, across four layers that fail over on different terms. Application servers are stateless and can be shifted; Redis, Kafka and Elasticsearch each replicate and recover on their own semantics, so there was never a single fact called "the cluster failed over" to verify.
Design
The application went from one cluster to two across two regions, then to three. The infrastructure moved to three in a single step rather than incrementally. The target was for a single surviving cluster to sustain serving capacity while the stateful systems continued to maintain correct replication behavior.
Verification
A failure drill removed two of the three clusters at once under production-scale load, measuring throughput on the survivor and replication lag on every stateful layer.

Four layers, four different failover semantics, and no downtime window.

DISTRIBUTED SYSTEMS

Event-Driven Architecture With Real-Time and Resync Processing

Kafka · CQRS read model projection · rate-controlled backfill

Context
Product and member data lived in source-of-truth databases owned by upstream teams. Serving every API request from them loaded systems we did not own, so we consumed change events from Kafka and served reads from our own replica. A CQRS read model projection, with the ownership boundary at the event stream.
Problem
Steady state was hundreds to a few thousand events per second. Adding a single field to the product schema produced billions of resync events at once. Sent through the normal stream, live edits queued behind the backfill and consumer lag grew: a seller could update a product and not see it for hours.
Design
Same topic, same consumer group. An event type field let the consumer branch into a real-time path and a resync path. The consumer's throughput budget was roughly 10K events per second; real-time took what it needed, typically around 1K per second, and the resync path was rate-controlled to consume only the remaining headroom. This was the design I proposed.
Ordering
A resync batch is a snapshot taken at one point in time, so a stale resync event must not overwrite a newer edit. The snapshot publish time is the boundary: real-time events after it always win. The comparison is against that batch boundary rather than a per-event clock comparison.

Eventual consistency was a domain judgment. The same structure would be wrong for inventory decrement or account balances.

OPERABILITY & AUTOMATION

Automated Production Log Triage Across 10+ Services

Scheduled CI job · coding agent · knowledge base in version control · Jira automation

Problem
Ten or more services logged in different shapes into one operational inbox. The recurring cost was re-deciding every day that a recurring error or warning is still benign, and occasionally missing the one that was not.
Design
A scheduled job runs once a day on a CI runner. A coding agent pulls the day's logs from every service into a common format, then evaluates each error and warning against a knowledge base of prior team judgments that lives in version control beside the code.
Output
Routine findings roll into a daily report for service owners. Critical errors open a Jira ticket and alert the owner directly.
Closing the loop
Operator corrections land as pull requests against the knowledge base, so a misjudgment is corrected once instead of re-explained, and every change to the triage rules is reviewed like code.
